# The bootstrap root

Generated by `cs-image-system bootstrap` from `bootstrap.yaml` at the root of this
tree (stage 70). Every run regenerates this directory from the answers file;
nothing here is edited by hand, and no run ever plans or applies it: applying is
the operator's act, below. `bootstrap.auto.tfvars` carries the answers, so the
apply needs nothing typed again; no secret value is in it or in the state.

## Apply

Terraform acts as whoever these name -- the same identities the interview asked as:

- `AWS_PROFILE`: the profile the interview probed the account as; its session must be live (`aws sso login`), and it must be allowed to write IAM
- `GOOGLE_OAUTH_ACCESS_TOKEN`: your active `gcloud` account's token, which the google provider prefers over application-default credentials (those may impersonate a runtime's service account that can read no IAM); it lasts about an hour
- `GITHUB_TOKEN`: the github provider's token; `gh` must be logged in as someone who administers the repository

```sh
export AWS_PROFILE=noaa
export GOOGLE_OAUTH_ACCESS_TOKEN=$(gcloud auth print-access-token)
export GITHUB_TOKEN=$(gh auth token)
cd generated/bootstrap
tofu init                      # the tree's declared backend
tofu plan                      # read it: nothing here is gated by the system
tofu apply
cd ../..
bash generated/bootstrap/set-secrets.sh
```

- The nine secrets' VALUES: one file per secret under the secrets directory (`_uncommitted/secrets`, never committed), then `bash set-secrets.sh` (CI_SETUP.md 3.7).
- The age identity for CI (CI_SETUP.md 3.6): `age-keygen`, the public key into encryption.recipients, `reencrypt`.
- The values in `.github/workflows/ci.yml` still marked REPLACE-ME: PERFORM_RUNTIME, GUARD_RUNTIME and AWS_REGION are set as Actions variables by this root, but the workflow reads its own literals until a release makes it read `vars`.
- Ask the org's Okta admins to confirm the API services app grants no `*.manage` scope and allows private-key client authentication only: its read scopes cannot see its own record, so the bootstrap could not check either.
- The OPA service user and its API key pair (`TF_VAR_KEY` / `TF_VAR_SECRET`) are made by hand in the OPA console; set-secrets.sh reads them from files (CI_SETUP.md 3.5).

## What a destroy would take that this root did not make

A `tofu destroy` here removes these as well; they were adopted or granted,
not created, and whatever else relies on them loses them:

- the READ role `csis-github-readonly`, adopted by import: the destroy deletes the role itself, with every subject it trusted (`repo:infrastructurebuilder/cs-image-system-3:*`, `repo:infrastructurebuilder@50206755/cs-image-system-3@1373601731:*` among them)
- the WRITE role `csis-github-apply`, adopted by import: the destroy deletes the role itself, with every subject it trusted
- the project roles `roles/compute.viewer` of the READ account `csis-github-readonly`, which already existed: every tree that reads the account relies on what it holds
